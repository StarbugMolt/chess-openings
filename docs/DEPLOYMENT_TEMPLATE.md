# Deployment template provenance

The Docker images, Symfony skeleton, host deployment controller and controller tests were adapted from [Starbugstone/test-auto-deploy](https://github.com/Starbugstone/test-auto-deploy) at commit `76e1ca9f956bd5a1542c159ea44be1a1b0a591e5`.

`scripts/o2switch/` and `tests/o2switch/` retain the template's controller lifecycle and tests. The interactive setup helper was extended to configure the project's installed custom Symfony hooks; its tests cover that path and private credentials. Project-specific build/preparation recipes are in `scripts/deploy/`. The template's demo controller/migration and legacy SSH upload workflow were excluded. Vue uses strict TypeScript here. Local Compose adds Mailpit, aligns PHP's worker UID for private checkouts and runs all dependency/build/test commands in containers.

Production follows the template's host-pull flow: successful main push CI, private host build, preparation, atomic activation and health/release verification. The controller starts disabled. This application's O2Switch target has not been provisioned or tested.

The preparation recipe runs `app:database:prepare` under the shared database operation lock: schema migrations, the first pinned source import only if no active catalogue exists, then separate lesson data migrations. Failed phases prevent cache warmup/release activation. Later deployments retain an existing catalogue; weekly refresh stays separate. Shared sessions and rotating private logs survive releases. The full PHP sync/status/rollback commands are locally verified; no host job is installed. See [MIGRATIONS.md](MIGRATIONS.md) and [CATALOGUE.md](CATALOGUE.md).

Use the [implementation plan](IMPLEMENTATION_PLAN.md#14-automatic-o2switch-deployment) and the pinned template's [host setup guide](https://github.com/Starbugstone/test-auto-deploy/blob/76e1ca9f956bd5a1542c159ea44be1a1b0a591e5/docs/o2switch-setup.md) for provisioning. Install with `bash scripts/deploy/install.sh /home/ACCOUNT/apps/chess-openings`, configure `profile=custom`, `health_mode=symfony` and the installed custom hooks. Never run this example against an unrelated deployment root. Controller updates require the template's disable/wait/reinstall/check/enable maintenance procedure.

## Review hardening (local implementation)

The custom build disables npm lifecycle scripts and all Composer plugins/scripts. The runtime bridge is generated directly from the locked Symfony Runtime template; Vite/esbuild still build with `npm ci --ignore-scripts`. npm's cache lives in the disposable build directory. This reduces dependency installation hooks; source/build dependencies still execute as the hosting account during the explicitly configured build.

Preparation refuses development/placeholder configuration before changing the database: production mode without debug, a random 64-character hexadecimal secret, the real HTTPS origin, a real SMTP transport and sender, and configured database credentials are required. Verified host-local SMTP/Exim or `sendmail://default` is allowed only with explicit `ALLOW_LOCAL_MAIL_TRANSPORT=1`; null transports, Mailpit and placeholders remain rejected. The configurator asks for that opt-in, and delivery on the actual host remains unverified. Both production examples contain SMTP/sender settings and a test prevents their drift. The interactive configurator prompts for SMTP credentials without echoing them. Existing host credentials stay intact; invalid preserved values must be corrected before preparation can succeed. Custom Symfony preflight checks private environment/token/key files, required PHP extensions, Composer and `mariadb-dump` as well as Node/npm/Git/tar. Install the MariaDB client on hosting and verify it can read the application's dedicated database.

Before every `app:database:prepare --lock-timeout=120`, the installed private `production.php` helper writes a transaction-consistent SQL snapshot using `mariadb-dump`. Credentials travel in a temporary mode-600 client option file, never argv; partial dumps and credentials are removed on success/failure. The private `shared/backups/` directory is mode 700 and retains the last three successful mode-600 deployment snapshots. A failed backup prevents migrations. This is an operational default, **not** an approved personal-data retention policy: the owner still needs to choose/document account/back-up expiry and off-host backup policy before public launch. Backups do not replace a host-tested restore procedure. Database migrations must use expand/contract changes compatible with the previous retained application code. An application rollback never restores SQL automatically; incompatible changes require explicit database recovery from a verified backup.

Each release records its original hashed assets in a private inventory. Activation copies the original assets from the other retained releases (two with the default retention of three); copied assets do not propagate indefinitely. Code rollback copies newer retained chunks too, so recently opened tabs can still load them. `index.html` receives `Cache-Control: no-cache`, and `/assets/` gets an immutable one-year cache. Retention remains bounded; tabs older than retained releases can need a reload. The wrapper's 15-minute execution deadline is passed to the controller, which refuses cutover unless the full stale-worker health window plus 60 seconds remains. The old release stays active if preparation uses the available budget. SIGKILL, machine failure and hosting-specific timeout behavior still need deployed failure testing.

Deploy pruning only removes release-ID log files. The separately installed `control/opening-sync.sh` wrapper calls only PHP, rotates its private `shared/log/openings-sync.log` at 1 MB (one previous file), and cannot be pruned as a deployment log. `run.sh` separately rotates `logs/cron.log` at 1 MB. Both wrappers emit a generic failure message outside the private log so a configured cPanel cron email recipient can receive alerts. Configure/verify the actual recipient and token-expiry monitoring on hosting. An interrupted recorded build requires inspection and explicit `retry`; repeated polling does not silently start an unbounded retry loop.

Apache adds Permissions-Policy, same-origin opener policy, and HSTS only for HTTPS requests. CI cancels superseded runs per ref and runs locked Composer/npm security audits. Dependabot also scans Compose image references at repository root with the [documented `docker-compose` ecosystem](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories). CI checks that the Playwright package and image versions match. The pinned checkout action upgrade, digest pinning and grouping Playwright package/image updates remain dependency maintenance work; do not update immutable pins without resolving and testing the actual supported versions.

Locally verified review commands: `php tests/o2switch/deploy-test.php`, `php tests/o2switch/health-test.php`, `php tests/o2switch/setup-test.php`, `bash tests/deploy/prepare-test.sh`, `bash tests/deploy/build-test.sh`, `php tests/deploy/production-test.php`, container installer/terminal checks, Apache routing/HTTP-01/smoke/cache-header checks, `composer audit --locked --no-interaction` and `npm audit` (no advisories). Isolated container dependency installation/build also passed with npm lifecycle scripts disabled; isolated Composer installation with plugins/scripts disabled and the generated runtime bridge boots the console. These checks use disposable files/databases and have not deployed, installed cron or proved O2Switch restore/SMTP/HTTPS behavior.

Account token responses finish before synchronous SMTP. Apache disables gzip/Brotli for `/api/auth` responses to preserve exact Content-Length framing. Before deployment, verify FastCGI/LiteSpeed `finish_request` support or that the actual proxy/compression path preserves response completion while SMTP is stalled. This host gate remains pending.

`docker compose build app` and `bash tests/deploy/backup-restore-test.sh` also passed: the rebuilt container includes the real MariaDB client, and a uniquely created disposable database recovered its original row from the private SQL snapshot. The test drops its database and removes temporary backup/option files afterward; the shared development catalogue and Mailpit are untouched.
